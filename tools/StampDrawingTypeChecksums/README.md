# StampDrawingTypeChecksums

Stamps corporate-lock checksums into `StingTools/Data/STING_DRAWING_TYPES.json`.

## What it fixes

`DrawingTypeRegistry.ComputeChecksums` already implements drift detection: it hashes every
corporate `DrawingType` at load and, when a shipped checksum disagrees with the computed one,
logs a warning and flips that type's `origin` to `"project"` so downstream code knows the entry
is no longer canonical.

The shipped catalogue never carried `checksum` fields, so the whole branch was inert — a
hand-edit to the corporate baseline on disk was silently accepted as corporate. That is finding
C-5 in `docs/DRAWINGS_PRODUCTION_REVIEW.md`.

## Why it is a C# tool and not a Python script

The value hashed is:

```csharp
SHA256(JsonConvert.SerializeObject(drawingType, Formatting.None))   // with Checksum nulled first
```

That is a hash of the **C# object's serialisation**, not of the file's bytes. Reproducing it in
another language would mean re-implementing Newtonsoft's property ordering, every
`NullValueHandling` attribute, every POCO default (`Origin`, `Scale = 100`,
`Orientation = "Landscape"`, `Discipline = "*"`, …) and the `TolerantScaleConverter` write path —
and then keeping all of that in step with `DrawingType` forever.

A **wrong** checksum is worse than no checksum: it makes every type report drift on first load,
flipping all 93 to `origin = "project"` and disabling the corporate lock completely.

So this project compiles the model itself:

```xml
<Compile Include="../../StingTools/Core/Drawing/DrawingType.cs" />
<Compile Include="../../StingTools/Core/Drawing/AnnotationRulePack.cs" />
```

Those two files hold the entire `DrawingType` object graph — `DrawingSlot`, `IsoNaming`,
`DrawingCropStrategy`, `SectionMarkerSpec`, `PrintOverride`, `AnnotationTokenProfile`,
`ProductionRule`, `TitleBlockVariantRule`, `AnnotationRulePack`, `AutoAnnotationRule`,
`SpotAnnotationRule` — and neither references the Revit API, so they compile standalone against
`net8.0` + Newtonsoft. The hash produced here is therefore generated by literally the same source
the plugin runs, and stays correct as the model evolves.

## Usage

Run from the repository root (it also walks upward to find the catalogue):

```bash
# stamp — rewrites the catalogue in place, then re-reads and re-hashes to verify
dotnet run --project tools/StampDrawingTypeChecksums

# verify only — non-zero exit if any corporate type has a missing or stale checksum
dotnet run --project tools/StampDrawingTypeChecksums -- --check
```

`--check` is suitable as a CI gate. It is not wired into a workflow yet; the plugin workflows name
specific `.csproj` paths, so this project is not built by CI today.

## When to re-run

**Any time `STING_DRAWING_TYPES.json` changes, and any time a field is added to or removed from
`DrawingType` or `AnnotationRulePack`** — a model change alters the serialisation and therefore
every hash, even with the data untouched. Forgetting means every type reports drift in Revit and
silently demotes itself to `origin = "project"`.

## Writing style

Checksums are inserted as a single `"checksum": "…"` line after each entry's `"origin"` line, by
editing the raw text rather than re-serialising the library. The shipped file mixes raw UTF-8
em-dashes with `\uXXXX` escapes, so a round-trip through `JsonConvert` would renormalise every
such string and turn a 93-line change into a whole-file rewrite. The stamping run produces
exactly 93 added lines and no deletions.

## View style packs are deliberately not covered

`ViewStylePack.Checksum` exists as a property but `ViewStylePackRegistry` has no
`ComputeChecksums`, so packs carry no corporate lock. That is a deliberate asymmetry — see the
Drawing Template Manager section of `CLAUDE.md` for the reasoning.
